# Fiche de reprise du projet PILIQI

Cette branche (`claude/pilotage-reprise`) ne contient que les notes de pilotage du projet. Elle ne touche jamais le code et ne se fusionne jamais. Elle permet à une autre session Claude, sur ce compte ou sur un autre, de continuer le travail exactement comme la session qui l'a écrite (2 au 26 octobre 2026).

- `README.md` : cette fiche, écrite à la main. Elle dit par où commencer, comment travailler et où tout se trouve.
- `ETAT.md` : l'état du dépôt et de la chaîne, régénéré automatiquement à chaque mise à jour.
- `VERIFICATION.md` : la dernière relecture à froid de cette fiche, écrite par l'étape `<lot>:fiche` après chaque lot (la première relecture a été faite à la main le 26/10/2026 au soir, avant le lot TA ; ensuite, après chaque lot, à partir de TA, l’étape de PU ayant été arrêtée pour insérer la série 9).
- `notes/` : les fichiers de décision de l'éditeur, les cahiers des charges, les plans, les scripts de la chaîne, l'installation (`notes/installation/`), l'historique complet (`notes/historique/`, dont les messages de l'éditeur et les résumés de la session, régénérés à chaque mise à jour, § 10) et le script de mise à jour de cette branche.

Le code est sur la branche de travail `claude/saas-invoice-editor-architecture-q6eizh` (PR #1 de besnikpiliqi/piliqiediteur, dépôt privé). `CLAUDE.md` de cette branche fait foi pour les règles du projet, sauf sur les sujets où une décision plus récente de l'éditeur l'emporte en attendant le lot qui la reporte dans `CLAUDE.md` (liste au § 7).

## 0. Par où commencer

### Pour l'éditeur, sur l'autre compte

1. Arrêter l'ancienne session (§ 1) : lui écrire, quand elle ne travaille pas, « Passation : laisse le lot en cours aller jusqu'à sa poussée et à la mise à jour des notes, n'en commence pas d'autre, arrête la course, lance pilotage-sync.sh "Passation", puis écris C'est fini. » Une fois « C'est fini » reçu, archiver l'ancienne session.
2. Créer l'environnement cloud de l'autre compte (menu de l'environnement dans la barre de titre de la session, puis Modifier) : relier le compte GitHub à https://claude.ai/connect-github et y installer l'application GitHub de Claude sur le dépôt privé besnikpiliqi/piliqiediteur ; ajouter ce dépôt sous « Repositories » dans les réglages de l'environnement (sans cela, le script d'installation ne peut pas lire le dépôt ; rubrique absente de l'environnement « Default ») ; accès réseau qui permet apt, Packagist et GitHub. Le script d'installation (champ « Setup script », décrit dans `notes/installation/ENVIRONNEMENT.md`, § 4) est facultatif la première fois : sans lui, la nouvelle session lance elle-même `installer-session.sh`, puis prépare le texte complet à coller. Ce script extrait aussi la branche de travail quand l'arbre est sur `main` et propre, car `main` ne contient que le commit initial. Aucun secret n'est nécessaire pour continuer : les tests utilisent des implémentations factices. Les identifiants SUPER PDP ne se mettront qu'à l'étape 2, par l'éditeur lui-même, dans les variables de l'environnement, jamais dans la conversation.
3. Ouvrir une session sur le dépôt, en choisissant la branche `claude/saas-invoice-editor-architecture-q6eizh` si l'écran le propose, et lui écrire ce message :

> Tu reprends le développement de PILIQI. Lis d'abord la branche claude/pilotage-reprise du dépôt besnikpiliqi/piliqiediteur, en commençant par README.md, puis fais exactement ce que dit son § 0 « Pour la nouvelle session ». Travaille en français. ultracode

Le mot « ultracode » autorise la session à lancer les chaînes d'agents (outil Workflow), dont toute la méthode dépend.

### Pour la nouvelle session

1. Ne rien commencer tant que l'éditeur n'a pas confirmé que l'ancienne session est arrêtée (§ 1).
2. Récupérer la branche de travail, puis cette branche et ses notes, et adapter les chemins (§ 4, points 1, 2 et 4). Vérifier que `ETAT.md` porte le message « Passation » et que « Commits locaux pas encore poussés » et « Travail non commité » sont vides. Sinon, `origin` fait foi : ce qui n'est pas poussé est perdu et se refait (§ 1), et les lots restants se calculent sur `origin` (§ 5). Lancer ensuite `bash <scratchpad>/installation/installer-session.sh --verifier`, et l'installation complète si un point manque (§ 4.3), puis les deux tests ciblés de `notes/installation/ENVIRONNEMENT.md` (§ 6), un par moteur, chacun au code 0, avant toute chaîne.
3. Lire, dans cet ordre : `CLAUDE.md` de la branche de travail, en entier (si la session a démarré sur `main`, ni lui ni les skills de `.claude/skills/` n'étaient dans son contexte au démarrage ; `REGLES` de `serie8-lots.js` dit déjà aux agents de lire `CLAUDE.md` en entier) ; cette fiche ; `notes/historique/DIRECTIVES.md` (au moins son § 0, « L'essentiel en quinze lignes », puis le reste) ; `ETAT.md`, et `VERIFICATION.md` (la première version a été écrite à la main le 26/10/2026 au soir, avant le lot TA ; chaque étape `<lot>:fiche` la remplace ensuite) ; `notes/historique/HISTORIQUE.md`. `notes/historique/messages-editeur.md` (tous les messages de l'éditeur à la session d'origine) et `notes/historique/resumes-de-session.md` (ses résumés successifs) servent à retrouver un détail ; ceux d'une session suivante sont dans `messages-editeur-<8 premiers caractères de son identifiant>.md` et `resumes-de-session-<…>.md` (§ 10).
4. Vérifier la CI de la dernière tête poussée, puis calculer les lots restants (§ 5) et relancer la chaîne (§ 5 et § 6).
5. Dire à l'éditeur, en le vouvoyant et en quelques lignes simples, où en est le projet et ce qui va se passer, puis tenir cette branche à jour à chaque changement (§ 10).

## 1. Règle d'or : une seule session à la fois

Deux sessions qui travaillent en même temps sur la branche de travail se détruisent leur travail. Avant de commencer :

1. L'éditeur arrête l'ancienne session par le message de passation du § 0 (ou confirme qu'elle est arrêtée). Ne jamais démarrer tant qu'une chaîne y tourne. Ce message fait finir à l'ancienne session le lot en cours (poussée et notes), arrêter la course entre deux lots (§ 5) et lancer une dernière fois `pilotage-sync.sh "Passation"`, pour que `ETAT.md` montre l'état exact.
2. Le meilleur moment pour changer de session est entre deux lots, juste après une poussée. Dans `ETAT.md`, regarder « Commits locaux pas encore poussés » et « Travail non commité » : tout ce qui n'est pas poussé reste dans le conteneur de l'ancienne session et n'arrive pas dans la nouvelle. Un lot qui n'est pas entièrement poussé se refait en entier depuis la tête poussée (§ 5, « Lots restants »).
3. Lire les documents dans l'ordre du § 0.

## 2. Le mandat et la façon de travailler

`notes/historique/DIRECTIVES.md` donne chaque directive de l'éditeur mot pour mot, avec sa date ; ce qui suit en est l'essentiel.

- L'utilisateur est l'éditeur de PILIQI (SaaS français de facturation et de caisse ; Laravel 13, Filament 3.3, PHP 8.3, PHPUnit 12). Il n'a ni société ni magasin : ne jamais lui dire « vous, le propriétaire » ni « vos magasins ». Il délègue toutes les décisions techniques et demande de finir le logiciel en autonomie, jusqu'à un logiciel prêt pour la production, selon le protocole de rigueur de `CLAUDE.md` et sa feuille de route. Son premier message (le prompt maître du 02/10, `notes/prompt_maitre.txt`) garde des principes qui valent toujours : jamais d'exemple simplifié, jamais de règle métier devinée, pas de complexité inutile (Laravel reconnaissable), les questions à se poser avant de dire qu'une fonctionnalité est finie, une clé de cache qui porte toujours le locataire, un job qui porte son contexte, rien d'inutile ni de secret dans les journaux.
- Tout se fait et s'écrit en français (réponses, code, commits, documents), même quand il écrit en albanais. Jamais en albanais.
- Il veut la voie la plus sûre, même si elle est plus longue : chaque lot passe par une implémentation, deux relectures adversariales indépendantes, une correction, les suites complètes SQLite puis PostgreSQL au code 0, faketime aux instants de la grille du README, pint, puis la poussée et la CI verte. Il a refusé tout allègement du protocole (« On va pas changer rien »). Ultracode est activé chez lui : le travail substantiel s'orchestre avec l'outil Workflow. Les lots se font un par un, parce qu'ils touchent les mêmes fichiers et les mêmes bases de test, et que leurs relectures doivent porter sur un arbre stable ; il a demandé deux fois pourquoi, c'est la réponse.
- Un défaut se corrige partout où il existe, pas seulement sur l'écran où il l'a vu. Une explication ne remplace jamais un test ; les calculs se testent sur des milliers de cas.
- Comptes rendus : ne jamais prétendre avoir lancé un test qui ne l'a pas été ; ne jamais dire que PILIQI est sans erreur ; toujours distinguer ce qui a été vérifié de ce qui reste à valider ; ne dire « c'est fini » qu'après la relecture (une première version se présente comme telle).
- Une règle métier non tranchée (calcul, arrondi, obligation légale, droits) se soumet à l'éditeur, expliquée en détail, avec des options et une recommandation, au lieu de choisir. Il n'a pas de comptable : chercher les règles sur les sites officiels, ne jamais le renvoyer vers un comptable. Ses réponses s'écrivent aussitôt dans un fichier de décision de `notes/` (texte d'origine cité, puis règles), la chaîne lit ce fichier, et cette branche est mise à jour dans la minute. S'il change d'avis, la dernière version du fichier fait foi.

Une page privée (outil Artifact) a servi à lui montrer un lot (T2) et à recueillir ses décisions ; un autre compte ne peut pas ouvrir ces pages : en refaire une au besoin (sources dans `notes/decisions/`, `notes/gen-decisions.js`).

Après un commit qui change des migrations, lui rappeler `git pull`, `php artisan migrate:fresh`, `php artisan optimize:clear` et une nouvelle inscription (le lien d'inscription est dans `storage/logs/laravel.log` avec `MAIL_MAILER=log`) ; voir aussi `a-faire-apres-chaine.md` (OPENSSL_CONF, clé du journal d'audit).

## 3. Consignes de sécurité (à garder mot pour mot)

- Ne jamais demander à l'utilisateur de coller jetons, clés ou mots de passe dans la conversation ; ne jamais écrire d'identifiants dans les fichiers du dépôt.
- Identifiants seulement par variables d'environnement : SUPERPDP_URL, SUPERPDP_CLIENT_ID, SUPERPDP_CLIENT_SECRET, SUPERPDP_TRICATEL_CLIENT_ID, SUPERPDP_TRICATEL_CLIENT_SECRET, SUPERPDP_REDIRECT_URI ; INSEE_SIRENE_CLE, INPI_RNE_IDENTIFIANT, INPI_RNE_MOT_DE_PASSE, RECOMMANDE_CLE, RECOMMANDE_SECRET_RAPPEL, JOURNAL_AUDIT_CLE, JOURNAL_AUDIT_CLE_ID, JOURNAL_AUDIT_CLES_PRECEDENTES, EDITEUR_OPERATEURS, PILIQI_EDITEUR_EMAIL, CAISSE_SECURISEE_CLE_PRIVEE, CAISSE_SECURISEE_PHRASE_SECRETE.
- Le classificateur a refusé un essai réel avec identifiants en ligne (« Credential Leakage ») ; ne pas le contourner.
- Conseiller à l'éditeur de renouveler les deux secrets du bac à sable SUPER PDP après les tests.
- Ne jamais envoyer de vraie requête à SUPER PDP, La Poste, l'INPI, l'INSEE ni à l'annuaire de l'Ordre des experts-comptables : seulement des implémentations factices ou des environnements de test autorisés ; aucune donnée fictive en masse en production.
- `git stash drop` et `git push origin --delete` ont été refusés par le classificateur (Git Destructive) : ne pas les forcer ; demander à l'éditeur de supprimer lui-même une branche sur GitHub.
- L'éditeur a un jour collé une clé privée de développement dans la conversation : ne jamais la répéter. Les identifiants qu'il a envoyés en captures d'écran ne figurent dans aucune note.
- `notes/pilotage-sync.sh` refuse de pousser cette branche s'il trouve un en-tête de clé privée, un jeton de la forme `ghp_`, `github_pat_`, `sk-` ou `AKIA`, une adresse de messagerie personnelle (gmail, outlook, hotmail, yahoo…), ou la valeur (6 caractères au moins) d'une des variables ci-dessus définie dans l'environnement ou dans `~/.profile`, sauf une valeur publique écrite dans la CI du dépôt. Il ne voit pas un secret collé dans la conversation et jamais mis en variable : relire soi-même chaque nouveau fichier de notes avant de le synchroniser. Les notes ne contiennent aucune donnée personnelle de l'éditeur (le nom de son employeur, ses navigateurs et les identifiants de son poste ont été retirés de l'historique).

   `git -C /home/user/piliqiediteur fetch origin && git -C /home/user/piliqiediteur checkout claude/saas-invoice-editor-architecture-q6eizh && git -C /home/user/piliqiediteur pull --ff-only`.

## 5. La chaîne de lots

### Fonctionnement

- `notes/serie8-lots.js` contient `REGLES` (règles communes à tous les lots, dont la vérification sur les deux moteurs et, depuis le 26/10/2026, la grille faketime avant chaque commit qui touche aux dates et avant le dernier commit du lot, la lecture de `CLAUDE.md` en entier, et l'endroit où trouver un fichier qu'une note cite par un chemin de l'ancien dossier de travail), la liste `LOTS` (chaque lot : `id`, `phase`, `titre`, `complement` = cahier des charges et fichiers à lire) et la mécanique. Pour chaque lot demandé dans `args.ouverts`, dans l'ordre de `LOTS` :
  1. `<lot>:implementation` (commits du lot, suites vertes) ;
  2. `<lot>:relecture1` et `<lot>:relecture2` en parallèle (optique fidélité et métier ; optique sécurité, isolation et qualité, qui pose aussi les questions du § 45 du prompt maître : index, file d'attente, journal d'audit, transaction et course, API, évolution, clé de cache et contexte des jobs) : défauts confirmés seulement ;
  3. `<lot>:correction` s'il y a des défauts (un commit « Relecture du lot … ») ;
  4. `<lot>:poussee` (arbre propre, `git push` sans forcer) ;
  5. `<lot>:fiche` : un agent neuf relit cette fiche à froid, comme le ferait une autre session, la vérifie contre le dépôt et les notes, met à jour le § 6 et les références factuelles fausses, et écrit le reste de ce qu'il trouve dans `VERIFICATION.md` (règles et méthode : il propose, la session décide) ;
  6. `<lot>:notes` (lance `pilotage-sync.sh`, qui met cette branche à jour).
  La chaîne s'arrête, sans rien pousser, si un lot n'a pas de commit, si une relecture ne rend rien (agent sauté ou mort), ou si la correction ne rend rien ou aucun commit alors que les relectures ont trouvé des défauts ; elle s'arrête aussi si la poussée échoue. La session regarde alors pourquoi dans le journal de la course et reprend comme pour un lot interrompu (ci-dessous). Les agents des lots ne lisent pas cette fiche (seul l'agent de l'étape `:fiche` la relit) : elle s'adresse à la session qui orchestre, et ses consignes (arrêter, relancer) ne doivent pas être prises pour les leurs.
- Lancer : outil Workflow avec `scriptPath` = `<scratchpad>/serie8-lots.js` et `args` = `{"ouverts": [ ... les lots restants, dans l'ordre ... ]}` (de vrais tableaux JSON, pas une chaîne), sans `resumeFromRunId`. Si `ouverts` est vide, n'est pas un tableau ou contient un identifiant absent de `LOTS` (« lot21 », « T 3 »), la course ne lance aucun lot, l'écrit dans son journal (« Aucun lot lancé : … ») et rend `[]` en quelques secondes : relire son journal après chaque lancement.
- Lots restants : un lot est fait quand ses commits « (lot X) » sont sur `origin` et, si ses relectures ont trouvé des défauts, son commit « Relecture du lot X … » aussi. `ouverts` reçoit, dans l'ordre de `LOTS`, ceux qui ne sont pas faits. Ne jamais remettre dans `ouverts` un lot déjà poussé. Pour voir ce qui est poussé :
  `for l in TA EC L1 A7 S9-L S9-A 21; do echo "== $l"; git -C /home/user/piliqiediteur log --oneline origin/claude/saas-invoice-editor-architecture-q6eizh | grep -F -e "(lot $l)" -e "(lot $l " -e "Relecture du lot $l "; done`
  (après un `git -C /home/user/piliqiediteur fetch origin` ; la liste des lots est celle de « Reste dans la chaîne », § 6).
- Règle apprise : relancer SANS reprise (`resumeFromRunId`). La reprise peut manquer le cache et refaire des relectures déjà faites.
- Une course déjà lancée ne voit pas les modifications du script, sauf une sous-course pas encore appelée (le script est lu au moment de l'appel). Pour insérer un lot ou changer un cahier des charges, arrêter la course entre deux lots (après une poussée) et la relancer. Avant toute modification du script, en garder une copie (`serie8-lots.avant-<raison>.js`) et vérifier la syntaxe (`node --check` sur une copie où `export const meta` devient `const meta` et le corps est enveloppé dans une fonction `async`). Dans un script de course, `${…}` s'échappe en `\${…}` quand il doit arriver tel quel à l'agent (incident `PIPESTATUS`).
- Lot interrompu, dans le même conteneur, avec du travail resté dans l'arbre ou des commits du lot pas encore poussés : écrire un script de reprise comme ceux de `notes/reprises/` (consigne exacte de l'agent coupé sauvée dans un fichier, note de reprise, poussée, fiche, mise à jour des notes, puis la chaîne en sous-course avec les lots restants). Si l'implémentation est commitée, le script reprend à l'étape coupée (relectures sur la plage de ses commits, correction ou poussée), et le lot reste dans les lots à faire jusqu'à sa poussée : le retirer avant ferait pousser ses commits sans relecture avec le lot suivant. En sauvant la consigne (premier message utilisateur de son `agent-*.jsonl`), retirer l'en-tête ajouté par le harnais (« [Workflow harness — computed task] … ») et l'indentation de deux espaces de chaque ligne. Sur un autre conteneur, ne jamais lancer un script de `reprises/` : il suppose le travail non commité et les journaux de l'ancien conteneur.

### Dangers connus : ce qui coupe les agents

- Un message de l'éditeur envoyé pendant qu'un tour est en cours interrompt ce tour et arrête aussi toutes les courses Workflow en arrière-plan. C'est arrivé le 09/10 (chaque message redémarrait alors la session), le 25/10 à 23 h 40 UTC (T2) et le 26/10 à 10 h 46 UTC (T3). Garder les tours courts quand une chaîne tourne ; avant un long travail, prévenir l'éditeur (« ne répondez pas avant que j'écrive C'est fini ») ; il sait qu'il peut écrire sans risque quand la session ne travaille pas.
- Les redémarrages du conteneur (18, 19 et 24/10) et les limites d'usage (de session, hebdomadaire) coupent aussi les courses (S8-L, A4c, V2, FA1).
- Après chaque arrêt : vérifier la date du dernier `agent-*.jsonl` de la course et sa dernière ligne (« [Request interrupted by user] ») ; si l'agent est coupé, le relancer comme ci-dessus, et redémarrer PostgreSQL s'il le faut.

### Suivi

- Points de suivi par `mcp__claude-code-remote__send_later` (toutes les 3 à 4 heures) et guets en fond (`until grep … journal.jsonl`, 2 heures au plus). Lire le résultat d'une course par `json.load(...)['result']` ou dans son `journal.jsonl`.
- Dans `ETAT.md`, « étapes commencées » ne dit pas qu'une étape est finie : une étape est finie quand le `journal.jsonl` de sa course a une ligne `"type":"result"` avec la même `key` que sa ligne `"type":"started"`.
- Après chaque lot poussé (vu à un point de suivi) : vérifier sa CI, puis, dans un tour court, dire à l'éditeur en français simple ce que le lot change pour un magasin, avec un exemple chiffré, les défauts trouvés et corrigés par les relectures, ce que l'agent a laissé (« laisses »), ce qui est vérifié et ce qui reste à valider (`notes/historique/DIRECTIVES.md`, § 3.4). Si le lot change une migration (c'est le cas de T3), lui rappeler pour son PC `git pull`, `php artisan migrate:fresh`, `php artisan optimize:clear` et une nouvelle inscription.
- Durées : suite SQLite environ 4 min 30, PostgreSQL environ 11 min (4 processus), grille faketime de 17 instants depuis le lot T3 (12 avant ; le paragraphe « Suite sous faketime » du README du dépôt fait foi), environ 5 min chacun. Le résumé de PHPUnit sort en une ligne JSON : seul le code de sortie fait foi (`echo $?` juste après, jamais de tube après `git push` ou une suite).
- CI : vérifier la course GitHub de chaque tête poussée (`mcp__github__actions_list`, `list_workflow_runs` sur la branche de travail). Relancer une seule fois si une machine GitHub s'arrête ; une CI rouge pour une cause réelle se corrige. Si les courses échouent en 2 secondes sans machine (`runner_id` 0, comme le 18/10), c'est le quota de minutes ou le plafond de dépense de GitHub Actions : un seul commentaire sur la PR, et l'éditeur règle la facturation. Les erreurs 500 intermittentes de GitHub se réessaient.
- Pour les ateliers de conception (cahiers des charges), travailler sur une copie figée du code : `git archive` d'un commit, plus `vendor` en liens physiques et `vendor/composer` copié (sinon un `composer dump-autoload` dans la copie réécrit le vendor du dépôt). Tuer un processus par son PID, jamais `pkill -f` (il a tué le shell). Un appel d'outil refusé peut quand même avoir écrit des fichiers : vérifier.

## 10. Mettre à jour cette branche, à chaque fois

`bash <scratchpad>/pilotage-sync.sh "message"` copie les fichiers listés dans `pilotage-fichiers.txt` et les scripts de reprise dans `notes/`, régénère `ETAT.md`, vérifie l'absence de secret, commite et pousse `claude/pilotage-reprise`.

Il régénère aussi, à chaque lancement, les messages tapés par l'éditeur et les résumés successifs de la session, depuis la transcription de la session (`~/.claude/projects/-home-user-piliqiediteur/<U>.jsonl`), par `<scratchpad>/historique/extraire-historique.py`, qui retire clés, jetons, mots de passe, navigateurs et adresses personnelles. Un fichier par session : `notes/historique/messages-editeur.md` et `resumes-de-session.md` pour la session d'origine (identifiant `00d7e3b2-…`), `messages-editeur-<8 premiers caractères de U>.md` et `resumes-de-session-<…>.md` pour une session suivante ; les fichiers des sessions précédentes restent tels quels. Ces fichiers ne s'ajoutent jamais à `pilotage-fichiers.txt` : la copie du dossier de travail écraserait la version régénérée. Les données personnelles à retirer en plus se listent, une chaîne par ligne, dans `<scratchpad>/historique/retraits-locaux.txt`, qui n'est jamais publié ni ajouté à `pilotage-fichiers.txt` : une nouvelle session ne le reçoit donc pas, et le crée elle-même si un message de l'éditeur contient une donnée personnelle (relire chaque nouveau message avant la synchronisation).

L'éditeur veut que cette branche ait toujours les dernières notes, jamais seulement à la fin. La session le lance donc aussitôt après chaque changement : chaque nouveau message de l'éditeur (régénéré automatiquement ; s'il donne une consigne durable, sa directive s'ajoute d'abord, citée mot pour mot avec sa date et son numéro, à `<scratchpad>/historique/DIRECTIVES.md`) ; chaque décision ou réponse de l'éditeur écrite dans `notes/` ; chaque modification de cette fiche, d'un script de la chaîne ou d'un plan ; chaque lancement, arrêt, interruption ou reprise d'une course ; chaque point de suivi ; chaque résultat de CI. La chaîne le lance en plus après chaque lot poussé (étape `:notes`). Un nouveau fichier de notes (décision, consigne sauvée, script de reprise placé dans `<scratchpad>/reprises/`) s'ajoute à `pilotage-fichiers.txt` avant ce lancement, sinon il n'est pas copié. Cette fiche se modifie à la main dans `<scratchpad>/pilotage-reprise/README.md`, puis le script la commite avec le reste. Avant chaque lancement : `git -C <scratchpad>/pilotage-reprise pull --ff-only` (§ 4.4). Si la poussée échoue (code 4) : `git -C <scratchpad>/pilotage-reprise pull --rebase`, puis relancer le script.
